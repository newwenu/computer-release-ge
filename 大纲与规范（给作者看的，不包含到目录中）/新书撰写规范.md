# 《计算机系统通识》撰写规范

> 面向零基础但具备基本阅读能力的普通读者（高考生水平）。不假设任何前置知识，不含编程教学内容。目标是让读者"理解计算机系统如何工作"，而非"学会操作电脑"。

---

## P0：底线要求

### 准确性与时效性

- [ ] **技术事实准确**：二进制转换、编码规则、协议流程、硬件规格等必须验证无误。有疑问标注 `[待核实]`，后续必须查证并移除此标签
- [ ] **不混淆猜测与事实**：不确定的内容标注 `[待查证]`，不把推测当结论写。`[待查证]` 是临时标记，交付前必须查证并移除
- [ ] **不回避复杂性**：该讲的真东西要讲清楚，不能因为难就跳过去或用模糊表述糊弄
- [ ] **不恐吓读者**：安全章节讲风险时不制造恐慌，用"可能"而非"会"，说清概率和前提条件

### 读者意识

- [ ] **零假设**：每个概念从它存在的原因讲起。不出现"众所周知""显然""学过数学的都知道"等假设读者已知的表述
- [ ] **概念闭环**：每个新概念完成"为什么需要它→它是什么→它怎么工作"的闭环。不抛出术语后不解释
- [ ] **不假设读者已经读了前面的章节**：引用前文时，用一两句话简要回顾，不让读者必须翻回去找。前提：被回顾的内容在前文已充分展开；若前文只提及未展开，本章需完整解释，不能用"回顾"句式一笔带过

### 逻辑一致性

- [ ] **段落内部不自相矛盾**：同一段内前后表述一致
- [ ] **跨章节术语一致**：同一概念全书使用统一名称，包括大小写、连字符（如"冯·诺依曼"不用"冯诺依曼"，"Wi-Fi"不用"WiFi"）
- [ ] **术语使用原则**：首次出现给中英文对照（如"与非门（NAND gate）""中央处理器（Central Processing Unit，CPU）"），后续以中文技术写作的通用惯例为准，全书保持一致。有中文通用名称时用中文（如"与门""寄存器"）；无通用中文名时用英文（如 CPU、RAM、API）。算术逻辑运算表达式除外

## P1：核心体验

### 语气与口吻

- [ ] 用"你"直接对话，不用"读者""用户"等第三人称
- [ ] 语气平实、尊重，像给一个聪明但没学过计算机的朋友讲解
- [ ] 避免居高临下的措辞：不说"很多人不知道""新手以为"，直接陈述事实
- [ ] 避免替读者做判断：不说"你不需要记住"，说"这些概念接触多了自然就熟悉了"
- [ ] **优先用准确描述，不是生动比喻**：正确的做法是"寄存器是 CPU 内部的存储单元，容量仅数百字节，访问速度为纳秒级——在存储层次中容量最小、速度最快"，而不是"寄存器就像厨师手边的调味料"
- [ ] **区分标准术语与比喻**：技术文档/教材/规范中作为正式名称使用的词（翻译层、管道、握手、容器、守护进程、心跳等）是标准术语，不是比喻，不标注局限。否则为比喻，须标注局限
- [ ] **比喻必须生活常见、符合常理**：只用读者日常经验中真实存在的场景做比喻，不用生僻或强行类比。如果找不到自然贴切的比喻，宁可不比喻，直接用准确描述
- [ ] **不依赖比喻作为论证**：比喻只能辅助理解，不能替代准确描述。如果使用比喻，必须说明比喻的局限之处
- [ ] **局限超过一条，删比喻**：准确描述说清楚了的，加比喻反而引入偏差。局限说明越多，比喻越不必要

### 去水：评价词、程度副词与填充词

- [ ] **删掉废话**：删掉某句话后，读者对知识的理解不受影响→删。判断方法：删掉后重读上下文，信息量不变→废话
- [ ] **经典论点句不算废话**：领域内公认的经典论断（如"开源不等于免费"），且后文提供证据支持→保留。非经典论断仍按废话标准判断
- [ ] **评价词须处理**：删掉后所述事实不变→评价词。先删评价词，再重读整句；删后不通顺则重写整句，不只删词。如"重要的协议"→"协议"（删）；"核心决策之一是架构"→"需要决定架构"（重写）。"核心""基本""根本"等结构性定位词删后事实改变，不是评价词，保留
- [ ] **程度副词须处理**：遇到程度副词，先判断删掉后信息是否丢失。丢失→量化替代；不丢失→直接删。程度副词修饰强度或绝对性（如"非常""极大地""极小""几乎""经常"）。"常见"标记列举的非穷举性（"常见错误包括A、B"=举例，非穷举），删掉后语义从举例变为穷举，属结构信息词而非程度副词。量化替代示例："速度很快"→"每秒可执行数十亿条指令"；"容量极小"→"存储层次中容量最小的层级"；"容量极小（数百字节）"→"容量仅数百字节"；"几乎所有X都是Y"→"X中Y占比超过90%"
- [ ] **填充词须处理**：删掉后句子更清楚→填充词，删。如"实际上""说白了""值得注意的是"通常可以删

### 量化表达

- [ ] **能量化就量化**：不写"容量很大"，写"可达数 TB"；不写"速度极快"，写"纳秒级"。层级位置走"层级位置用比较句式"，跨数量级走"跨数量级给范围"
- [ ] **数据标单位**：不写"480"，写"480Mbps"；不写"4"，写"4 GB"
- [ ] **数量级优先**：无法给出精确数值时，给出数量级（"毫秒级""数十亿次/秒"）
- [ ] **层级位置用比较句式，不单点量化**：只写量化值无法解释"为什么是这个量级"时，先写比较句式再补典型量级，不钉死为绝对值。如"寄存器是存储层次中容量最小的层级，典型容量数百字节"
- [ ] **跨数量级给范围并标注"典型"**：如"主存容量通常为 8--128 GB"，不写单点值"16 GB"
- [ ] **技术术语中固化的程度词不去水**："高速缓存""低速设备"中的"高速""低速"是分类名，不去水；但解释时仍需给出量化

### 讲原理，不讲操作

- [ ] 不讲"点这个按钮→选那个菜单→输入什么"
- [ ] 讲"这个功能为什么存在、它解决了什么问题、它是怎么实现的"
- [ ] 如果需要举例说明某个概念，举例应服务于讲原理，不变成操作教程
- [ ] **跨平台差异**：Windows、macOS、Linux 的不同实现是对同一原理的不同体现。在讲原理时顺便指出差异，不写成"Windows 怎么做、macOS 怎么做"的并列教程

### 先讲为什么，再讲是什么

- [ ] 每个概念出现之前，先讲清楚：没有它之前有什么问题？它为什么被发明出来？
- [ ] 不要用"X 是 Y"的定义式开头，用"在 X 出现之前，人们面临的问题是..."的动机式开头
- [ ] 概念引入顺序符合历史发生顺序或逻辑推导顺序，不跳步

### 前置知识

- [ ] **前置知识用概念描述**：如"理解比特、字节、二进制计数"，不绑定到具体章节——读者可能从其他途径学过这些内容。如果涉及本书特有的概念或约定，再标注章节名

### 人物提及

- [ ] 当概念的发明动机涉及具体人物时，可以简要提及该人物和事件，但不超过 3 句话
- [ ] 聚焦"他解决了什么问题"，不展开生平或轶事
- [ ] 不为凑数而写人物——如果该概念的历史动机不涉及具体人物，不强行引入

### 误解消解

- [ ] 当某个概念容易被误解时，不用"你可能以为 X，但实际上 Y"的句式（居高临下）
- [ ] 直接给出准确表述，让误解自然消解。如不写"很多人以为 Unicode 就是 UTF-8"，写"Unicode 是字符编号的字典，UTF-8 是把这些编号存进计算机的方案——两者是不同的层次"
- [ ] **不堆否定面撑"但"**：读者不会怀疑C成立时，不用"不A，不B，但它确实在C"制造反差。为撑"但"而堆否定面易夸大失实（如"算盘没有运动部件"），直接陈述事实

### 举例本土化

- [ ] 举例时优先选择中国读者熟悉的场景（如用"微信"而非"WhatsApp"，用"百度"而非"Google"）
- [ ] 不专门设置"中国案例"章节或栏目，不讨论政策或审查相关内容

## P2：格式规范（Quarto）

### 文件与项目结构

- [ ] 源文件使用 `.qmd` 扩展名
- [ ] 每章一个独立文件，文件命名：`序号-章节名.qmd`（如 `01-什么是信息.qmd`）
- [ ] 项目配置文件 `_quarto.yml` 中定义章节顺序和元数据
- [ ] 图片放在 `images/` 目录下，按章节分子目录

### 标题层级

- [ ] `#` 仅用于书名（全书唯一），不出现在章节文件中
- [ ] `##` 章标题（如 `## 什么是信息 {#sec-what-is-information}`）
- [ ] `###` 节标题
- [ ] `####` 细分节标题（尽量不超三层）
- [ ] 章节编号连续，无重复、无遗漏

### 列表

- [ ] 步骤式内容用编号列表（`1.` `2.` `3.`）
- [ ] 并列要点用项目符号（`-`）
- [ ] 嵌套列表缩进一致（两个空格或四个空格，全书统一）

### Callout 块（Quarto 标注）

使用 Quarto 原生的 callout 语法（不用 markdown 的 `>` 引用块）：

- [ ] `前置知识` —— `{.callout-note}`，放在章标题之后、正文之前
- [ ] `在现实中` —— `{.callout-note}`，放在本章小结之后、延伸阅读之前。写法要求：
  - 描述现象，不描述操作步骤（与"讲原理，不讲操作"一致）
  - 通常 1-2 句话，不展开论证
  - 必须与本章核心原理直接相关，不做泛泛的"计算机很有用"式关联
- [ ] 延伸阅读推荐 —— `{.callout-tip}`，放在每章末尾
- [ ] 重要提醒  `{.callout-warning}`
- [ ] 补充说明  `{.callout-note}`

### 代码与术语

- [ ] 技术术语、命令、按键、路径使用反引号（如 `Ctrl+C`、`C:\Users`、`ping`）
- [ ] 代码块标注语言类型（如 ` ```bash `、` ```text `）
- [ ] 不是代码的不要放进代码块

### 交叉引用（Quarto）

设置 ID 和引用语法：

- **章节 ID**：在标题后添加 `{#sec-xxx}`，如 `## 二进制 {#sec-binary}`
- **图表 ID**（三种形式，统一目标：使 `@fig-xxx` 交叉引用可用）：
  - 外部图片：`![图：ALU 结构](images/03-alu.png){#fig-alu}`
  - Mermaid：`%%| label: fig-alu`（在代码块内第一行）
  - HTML 容器：`:::: {#fig-alu}`（容器开标签）
- **表格 ID**：在表格标题后添加 `{#tbl-xxx}`

引用时使用：

- [ ] 引用章节：`@sec-chapter-name`（Quarto 自动生成编号）
- [ ] 引用图表：`@fig-diagram-name`、`@tbl-table-name`
- [ ] 引用延伸阅读书目：使用 BibTeX key（`@petzold2000code`），由 Quarto 自动生成引用格式
- [ ] **不手写"参见第 X 章"**，全部走 Quarto 的交叉引用机制，避免编号变动时手动更新

### 图表

所有图表必须有唯一 ID 和人类可读标题，使 `@fig-xxx` 交叉引用可用。三种形式：

**形式一：外部图片**（照片、截图、导出的 SVG/PNG）

- [ ] 语法：`![图：标题](images/NN/文件名.扩展名){#fig-xxx}`
- [ ] 照片或截图放在 `images/` 目录，按章节分子目录（如 `images/08/`）
- [ ] 标题直接说明内容，编号 `{#fig-xxx}`；行内图标不编号

**形式二：Mermaid 代码块**（流程图、时序图、架构图）

- [ ] 语法：

  ````markdown
  ```{mermaid}
  %%| label: fig-xxx
  %%| fig-cap: "图表标题"
  flowchart TB
      A --> B
  ```
  ````

- [ ] `%%| label: fig-xxx` 提供交叉引用 ID
- [ ] `%%| fig-cap: "标题"` 提供图表标题（Quarto 自动编号为"图 X.Y：标题"）
- [ ] 代码块后**不要再写纯文本标题**（如"图：xxx"），`fig-cap` 已承担此功能
- [ ] 架构图、流程图、时序图优先使用 Mermaid，不用外部图片

**形式三：内嵌 HTML/SVG 容器**（Mermaid 无法表达的复杂技术图解）

- [ ] 语法：

  ````markdown
  :::: {#fig-xxx}
  <style>
  /* 样式 */
  </style>
  <div class="chart">
    <svg>...</svg>
  </div>

  图：图表标题
  ::::
  ````

- [ ] `:::: {#fig-xxx}` 提供交叉引用 ID
- [ ] 容器末尾写 `图：标题`（纯文本，Quarto 将其作为图注）
- [ ] 仅在 Mermaid 无法满足需求时使用（如需要精确 SVG 绘制、CSS 动画）
- [ ] 优先考虑：能否用 Mermaid 表达？能则不用此形式

**选择优先级**：Mermaid → 外部图片 → HTML/SVG 容器

### 图片占位

撰写章节时，暂时无法获取的图片用占位语法：HTML 注释说明画什么，图片引用行照写 `{#fig-xxx}` 标签。语法：`<!-- [待制图] 描述：... -->` 后接 `![图：...](images/NN/xxx.png){#fig-xxx}`。图片文件不存在时 Quarto 警告但不阻断构建。可用 Mermaid 表达的图直接写 Mermaid，不用占位。四种占位标记：`[待制图]`（手绘示意图）、`[待截图]`（界面截图）、`[待拍照]`（实物照片）、`[待获取]`（外部获取）。不创建空文件或占位 PNG，制图完成后放入 `images/NN/` 目录即可。

### 图片获取与版权

- [ ] **界面截图**：自行截图，截图前关闭无关窗口、隐藏个人信息，分辨率不低于 150 DPI
- [ ] **行内图标**：尺寸 16–24 px，命名加 `icon-` 前缀，放 `assets/icons/` 或 `images/NN/`，不编号、不加图注
- [ ] **硬件照片**：优先用厂商公开资料（标注来源），其次用 CC BY/CC BY-SA 授权图片，不用来源不明或带水印的图片
- [ ] **概念示意图**：自行绘制（Excalidraw、draw.io、Figma），导出 SVG/PNG，风格统一
- [ ] **非自制图片**：标注来源和授权协议
- [ ] **不使用的来源**：搜索引擎图片结果、带水印图片、未授权图库
- [ ] 图表标题直接说明内容，编号 `{#fig-xxx}`；行内图标不编号

### 延伸阅读

每章末尾必须有延伸阅读区块，格式：

```markdown
::: {.callout-tip}
### 延伸阅读

- 作者《书名》—— 一句话说明推荐理由
- 作者《书名》章节范围 —— 一句话说明推荐理由
:::
```

- [ ] 书名使用中文书名号《》，不用""
- [ ] 推荐理由说明"这本书（或这几章）跟本章内容有什么关系"
- [ ] 延伸阅读列表中的每本书，在附录 B 的 BibTeX 库中需有对应条目（`.bib` 文件），以便正文中通过 `@citation-key` 交叉引用时自动生成参考文献格式

### 一般格式

- [ ] 无 emoji，无装饰性符号
- [ ] 中文引号使用 `""`，不用直角引号 `「」`
- [ ] 中文与英文/数字之间留空格（如"使用 Python 编写""第 3 代"）
- [ ] **破折号**：少用，仅用于简短的解释关系。"解释"不是频繁使用破折号的借口——许多场合该用逗号、句号或分号。同一段落不宜多次使用。审查时逐个检查：先判断前后句是什么关系（因果、转折、递进、并列、解释？），再选标点，不要跳过判断直接用破折号
- [ ] **术语后置**：读者不熟悉的概念，先描述机制再给术语名（用逗号+"这叫做"连接，不用破折号）；读者已从上下文理解的概念，术语前置更自然
- [ ] 文件末尾保留一个空行
- [ ] **格式无残留**：无多余分隔线（连续 `---`）、空标题、未闭合的格式标记（如孤立的 ` ``` `）

## P3：内容结构

### 每章结构

每章按以下顺序组织：

1. **前置知识**（callout block）
2. **正文内容**（按"为什么→是什么→怎么工作"的逻辑展开）
3. **本章小结**（一段话概括，不列清单，不用表格重复正文）
4. **在现实中**（callout block，1-2 句话，描述本章原理在读者日常中的对应现象）
5. **延伸阅读**（callout block）

### 标题说内容

- [ ] 章标题和节标题直接说这一节讲什么，不说重要性或评价。如"指令的格式与分类"而不是"指令系统的重要概念"；"拥塞控制"而不是"TCP 的关键机制"
- [ ] 标题让读者扫一眼就知道这一节的覆盖范围，不制造模糊期待

### 章节长度

以下字数是**自然写完后的典型范围**，不是写作目标。内容讲清楚了，字数自然落在这个区间。**禁止为了凑字数而添加内容**——违反 P1 去水原则的冗余文字，即使让字数达标也必须删掉。如果内容讲清楚了但字数偏少，说明该主题本身不需要更多篇幅，不需要强行扩充。

| 章节类型 | 典型字数范围 |
|----------|------------|
| 信息与编码（Part 1） | 8000-12000 字/章 |
| 硬件基础（Part 2） | 10000-15000 字/章 |
| 体系结构（Part 3） | 10000-15000 字/章 |
| 操作系统（Part 4） | 10000-15000 字/章 |
| 计算机网络（Part 5） | 8000-12000 字/章 |
| 软件与数据（Part 6） | 8000-12000 字/章 |
| 安全、隐私与前沿（Part 7） | 8000-12000 字/章 |

远超上限 → 信息密度可能不够或该拆章。远低于下限 → 检查是否有该讲但漏讲的内容，如果没有则不需要扩充。

每章新概念密度控制在 5-10 个。**密度**指任意时刻读者需要同时持有的新概念数，不是全章累计引入的总量。深潜型章节（概念引入后不退场）密度≈总量；管线型章节（概念依次出场又退场）密度远小于总量，总量可超过 10。

**密度计数方法**：逐节统计"本节新引入""本节搁置""本节退场"。概念有三个状态：

- **持有**：本节论证直接依赖，读者必须理解才能读懂 → 计数 +1
- **搁置**：本节不依赖，但后续某节论证仍需 → 计数 +0，记录搁置跨度
- **退场**：后续论证不再依赖 → 移出

搁置概念被唤醒时，根据跨度计入唤醒成本：搁置 1-2 节不计；3-4 节密度 +0.5；5 节以上密度 +1。回顾性提及（小结罗列、顺带举例）不算论证依赖，不触发唤醒。**概念粒度**：术语和它的实现工具一体两面不拆分（如"编译"和"编译器"计数为 1）；后续分别独立依赖的子概念各自计数（如"时间复杂度"和"空间复杂度"各计 1）；顺带提及未做闭环的不计数。**持有判据**：删掉本节对某概念的解释后，读者还能读懂本节核心论证吗？不能→持有（+1）；能→搁置（+0）。**节的定义**：`###` 和 `####` 均为计数的"节"，`####` 子节概念累积计入所属 `###` 行。

**密度超过 10 的处理**：

1. **精简**：应用已有规则——去水（删冗余）、推迟（非本章核心概念用交叉引用推迟到后续章节展开）、不展开（读者有日常认知基础的概念提及但不做完整闭环）。不删有价值内容
2. **拆分**：精简后密度仍超过 10，且满足拆分三条件时拆为两章：
   - 概念分组：两部分各自密度 ≤10
   - 叙事独立：每部分有独立的叙事弧线（有起因、展开、收束）
   - 依赖单向：两部分之间只有单向依赖（B 依赖 A 的结论，A 不依赖 B）
3. **保留**：精简后密度仍超过 10 且不满足拆分条件，在章节开头加阅读路线提示帮助读者分次阅读
